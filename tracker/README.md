# tracker — 顔の精度B：追跡を使う新しい構成（M1 マック）

人物の検出・追跡・顔の判定をマックで行い、クラウドには「来た・いる・去った」だけを送る。
経緯は Windows 側の引き継ぎメモ（2026-09-17）。

## 用意（2026-09-17）
- Python は uv で入れた 3.11（`~/.local/bin/uv`）。`/usr/local` の道具は使わない（sha256sum などがIntel用で動かない）
- `cd tracker && uv sync` で `.venv` ができる
- カメラの URL は `~/.arigato/tapo.env` に `TAPO_URL=rtsp://…/stream1` と本人が書く（リポジトリに書かない）

## 計測（カメラなし・zidane.jpg 1280x720・2人）
| 構成 | 追跡 | 顔（2人分） | 合計 |
|---|---|---|---|
| YOLO11n CPU ＋ 顔 CPU | 36ms | 249ms | 285ms |
| **YOLO11n CPU ＋ 顔 CoreML** | 33ms | 35ms | **68ms（15fps目標で14.4fps出た）** |
| YOLO11n MPS ＋ 顔 CoreML | 34ms | 42ms | 76ms |
| YOLO11n ONNX（CPU / CoreML）＋ 顔 CoreML | 40ms | 34ms | 74ms |

- 2304x1296 でも変わらない（人の枠の中だけで顔を探すため）
- YOLO の CoreML 書き出しは torch 2.14 と coremltools の組み合わせで失敗。CPU で足りているので追わない
- 顔は1人あたり約17ms。5人同時・毎コマなら約120ms → 顔は毎コマでなく、トラックごとに間引けば足りる
- プロセスのメモリ 約1.2GB

```
uv run python bench.py --src rtsp --fps 10 --secs 60          # 主ストリーム
uv run python bench.py --src rtsp --sub --fps 10 --secs 60    # 副ストリーム
```

## 実物のカメラでの計測（2026-09-18・キッチン）

- ログインは `thankU` で通る。9/17夜の401は、失敗が続いたあとの一時的なロックだった
- **映像は回っていない**。生のコマがそのまま正しい向き（マック側で回す必要なし）
- 主ストリーム（2304x1296）はほぼ届かない（0.1fps）。ラズパイが既に2本受けているため。**副ストリーム（1280x720・15fps）を使う**

| 条件 | 届いたコマ | 別々の瞬間として処理できた数 |
|---|---|---|
| 有線LAN（大学）を挿したまま・TCP | 0.1fps | 0.1fps |
| 有線を抜く・TCP | 8.5fps | 2.3fps |
| **有線を抜く・UDP（低遅延の設定）** | 12〜13fps | **5.0〜5.5fps** |

- 計算は余っている（1コマ 追跡39ms＋顔11〜18ms＝約52ms＝19fps相当）。**足りないのは通信**
- 電波が弱く、コマがまとめて届いては途切れる。まとめて届いた分は同じ瞬間なので、実質5fps
- 5fps は引き継ぎメモの想定（検出と追跡は5〜10fps）の下限。今の1.5秒おき（0.7fps）の7倍
- macOS が有線を優先すると Wi-Fi が眠る。**このマックに有線をつながない**こと

## 映像が切れたときの繋ぎ直し（2026-09-19・カメラには接続せずに実装と試験）

9/18 の記録は31分で映像が切れて終わった。24時間運転には自動の繋ぎ直しが要る。

- 切れたら繋ぎ直す。**すぐまた切れるときは待ち時間を倍にする**（4→8→…最大30秒）。
  最初の実装は待たずに繰り返し、1秒間に何十回もカメラを叩いた（手元の試験で発覚）
- 30秒以上もった接続のあとは、待ち時間を最初に戻す
- UDP では、届かなくなっても read() が失敗と言わずに待ち続ける。
  新しいコマが10秒来なければ、こちらから映像を切って繋ぎ直す（`kick`）
- 試験（手元の動画と、繋がらない宛先で確認）：暴走しない／止めたら増えない／kick で繋ぎ直す

## 固まる不具合の修正（2026-09-19・カメラには接続せずに試験）

9/19 14:07:07、コマが止まったので繋ぎ直そうとしたところ、プログラムごと固まり、
そこから 15:22 に手で止めるまでの **75分を取り逃した**。原因は2つ。

1. 読んでいる最中の映像を、別の流れから `cap.release()` で切っていた（OpenCV/FFmpeg で固まる）
2. RTSP に読み取りの時間切れが無く、コマが来なくなっても `read()` が永久に待っていた

直したこと：
- `timeout;5000000`（5秒）を RTSP の設定に追加。何も来なければ読み取りが失敗で返る。
  黙ったままのサーバを立てて確認：**5.2秒であきらめる**（以前は永久に待つ）
- `kick()` は映像に触らず「捨てる合図」を置くだけにし、`new_reader()` で**新しい読み手を作り直す**。
  古い読み手は時間切れで自分から終わる。作り直しは0.00秒で済み、固まらない（試験で確認）

9/19 13:33〜14:07 のコマの届き方（カメラが弱り始めた時刻の手がかり）：
300コマごとの速さは 4.0〜6.1fps を行き来し、**右肩下がりの傾向は無し**。14:06:18 まで普通に届き、
そこから60秒以内に完全停止。マックの副ストリームが止まったあとも、主ストリーム（PC側）は
16:42 まで写真を出し続けていた。

ログへ書く。次に映像が止まったとき、回線が原因かどうかをその場で切り分けられる。

## 9/19 夜の実機試験（20:38:16〜21:07:27・進行役の指示で途中終了）

わざと切る試験（開始10分後の予定）は**一度も実行されなかった**。その前に本物の切断が起きたため。

- 20:38〜20:44 コマの速さ 2.9〜3.2fps（昼は5.0〜6.1fps）。**始めた時点ですでに回線が悪い**
- 20:44:22 最後の正常な処理。**20:45:37 に切断し、21:07:27 に止めるまで一度も戻らず**
- その間、ping は通るのに 554番へのTCP接続が5秒で時間切れ。IP は 192.168.0.19 のまま
- PC の橋渡し側の最初の繋ぎ直しは 20:50:06。**マックのほうが4分半早く全損している**

反省と直し：22分で読み手の作り直し95回・繋ぎ直し99回（約4〜5回/分）と、弱った回線を叩き続けた。
作り直しても待ち時間を引き継いで倍にし（2→8→30秒で頭打ち）、記録側の作り直し間隔も
10秒→最大60秒まで延ばすようにした。同じ状況なら十数回に収まる。
