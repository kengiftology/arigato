# 止まったことに、どうすれば気づけるか（2026-09-24）

9週間の観察を、人が毎日見に行かずに成立させたい。
そのためには「止まったら気づける」が要る。2026-09-24 に、その仕組みの穴が2つ見つかった。
どちらも**実際に起きてから**見つかったもので、設計だけ見ていても気づけなかった。

## 穴1：本番の通り道に、会話の寿命に縛られるものを置いていた

### 起きたこと

9/24 13:20:34、キッチンのカメラからクラウドへ写真を送る「橋渡し」が止まった。
**復旧は 15:11:59。1時間51分25秒、記録が無い。**

きっかけは PC の Wi-Fi が切れたことだった。だが Wi-Fi は 14:04 に戻っている。
それでも橋渡しは戻らなかった。

原因は Wi-Fi ではなかった。**橋渡しを、Claude の会話の裏プロセスとして動かしていた。**
その会話が終わったとき、橋渡しも一緒に終了させられていた。
プロセスそのものが消えているので、「映像が切れたら繋ぎ直す」という作り込み
（9/22 に入れたもの）は何の役にも立たない。**起こす主体が居ない。**

### なぜ見落としていたか

橋渡しは 9/16 から PC で動いていて、その間ずっと「動いている」ように見えていた。
会話が続いているかぎり動くからである。**壊れ方が、会話が終わった瞬間にしか現れない。**
日中に何度も動作確認をしても、一度も再現しない。

### 直し

Windows のタスク `ArigatoBridge` から起動する形にした。
5分おきに「動いているか」を見て、居なければ起こす（`.arigato/bridge_run.ps1`）。
会話とは無関係に動く。

**確かめた**：15:13:08 にわざとプロセスを殺した → 15:17:38 に自力で起き上がった →
15:17:53 に稼働を確認。**空白は4分45秒、人手はゼロ。**

### 一般化

> **本番の通り道にあるものを、会話の裏で動かさない。**
> 動かすなら、その場かぎりの「見るだけ」のものに限る。

同じ観点で全体を洗ったところ、他の作業トークが持っていたものは
すべて「見るだけ」か、すでに Windows のタスクだった。
本番の通り道に居て、かつ会話の裏だったのは**橋渡しだけ**だった。

## 穴2：生死を「起動してから」で測っていた

### 起きたこと

橋渡しが死んでいた1時間51分のあいだ、見張り（10分おきに `/spirit/health?strict=1` を叩き、
落ちていればメールを出す）は **6回しか鳴らなかった**。
しかも **14:10 と 14:20 は「無事」と答えていた**。

### なぜか

生死の判定はこう書かれていた。

```python
t = _ALIVE[k]                 # この装置から最後に来た時刻
if t:
    ok = ago <= limit
else:
    ok = up <= limit          # 起動したばかりで、まだ来ていないだけかもしれない
```

`_ALIVE` はクラウドの**頭の中**にある。クラウドは1日に何度も起動し直す
（9/23 は19回）。起動のたびに `_ALIVE` は空になり、そのあと `limit`（カメラなら15分）の
あいだは、**装置が死んでいても「起動したばかりだから」で無事と答える**。

19回 × 15分 ＝ **1日あたり最大4時間45分、止まっているのに隠れる。**

### 直し

「最後に来た時刻」を状態と一緒に保存し、起動時に読み戻す。
`_save()` で `st["alive"]` に書き、`_health()` で読む。
15分の猶予は「**一度も来ておらず、保存された覚えも無い**」ときにだけ残る。

### 一般化

> **生死は「自分が起きてから何秒」ではなく「相手から最後に来てから何秒」で測る。**
> 見る側が起動し直したことを、相手の無事の理由にしない。

## 残っている穴（承知のうえ）

見張りの仕組みは、いま2つとも **この PC の中**にある。

- 橋渡しを起こすタスク（`ArigatoBridge`）
- GitHub の見張りを10分おきに叩き起こすタスク（`ArigatoWatchKick`）

**PC ごと落ちたら、どちらも動かない。**
PC は橋渡し本体でもあるので、いちばん困る壊れ方にいちばん弱い。
外側（Google Cloud の稼働監視など、この PC に依らない場所）から見る仕組みが要る。
2026-09-24 時点で未着手。本人の手が要る作業として残している。

## この経験から

2つとも、**設計を眺めていて気づいたのではなく、実際に止まってから**分かった。
1つ目は「会話が終わる」という、動作確認では再現しない条件で壊れた。
2つ目は「クラウドが起動し直す」という、正常動作の一部で穴が開いた。

観察を9週間続けるなら、**わざと壊して、戻るかを見る**ほかにない。
`docs/9月のタスク.md` の 4.3.1（1日放置して翌朝見る）・4.2.2（わざと止めて気づけるか）は、
そのための項目である。今回はその試験を待たずに本番で起きたが、
**起きた形をそのまま試験にできた**（4.3.1 は 9/24 の実例で置き換えた）。

なお 4.2.2 には、研究トークD の指摘で1項目が足された：
**「気づく仕組みそのものが、会話が終わっても生きているか」**。
鳴る仕組みが会話の裏プロセスなら、本番が止まったときに一緒に死んで、誰も気づけない。
今回とまったく同じ形である。
