# 仕様書：場所の変遷ビュー（環境のログ）

**対象機能：** ゾーンページを「その場所に何が起きてきたか」の時系列＝**環境の日記**に作り替える
**バージョン：** v1（2026-06）
**前提：** 既存の arigato アプリ（FastAPI / Firestore / GCS / PWA）に追加する

---

## 0. この機能は何のためにあるか（エンジニア向け背景）

このアプリは「共有空間の手入れ（掃除・改変）を記録し、手を動かした人にありがとうを届ける」研究用アプリ。

これまでは **人軸**（誰が何回手伝ったか）で記録を見せてきた。今回追加するのは **場所軸**：

> ある場所で「いつ・誰が・何をしたか（維持・改変）」が時系列で積み重なり、**その場所の変遷そのものが見えるようにする。**

なぜ重要か：研究の核心は「積み重ねが見える → 次の人が手を入れたくなる」という連鎖。その着火源が「場所の変遷の蓄積」になる。だから**場所を主語にしたタイムライン**が要る。

実装の心構え：**アプリは説明しすぎない。** 「綺麗になりました」と評価を書かない。起きた事実（手入れの記録）を時系列に並べるだけ。良し悪しの判断は現場にいる人がする。

## 1. 現状（既存実装）

### データモデル（Firestore コレクション）

| コレクション | 主なフィールド |
|---|---|
| `zones` | `name` |
| `maintenance` | `zone_id`, `zone_name`, `person_name`, `content`, `before_photo`, `after_photo`, `created_at`(ISO/JST), `completed_at`, `thanks_count`, `status`, `helped_by` |
| `thanks` | `maintenance_id`, `source`(`user`/`auto`), `sender_name`, `message`, `created_at` |
| `users` | `last_name`, `first_name`, `photo_url`, `created_at` |
| `push_subscriptions` | `person_name`, `subscription` |

`maintenance.status` の値：
- `in_progress` … ビフォーのみ（＝「気になっています」＝手伝い待ちの招待状）
- `completed` … ビフォー＋アフター揃い
- `after_only` … アフターのみ

`maintenance.helped_by`（**status とは独立したフィールド**）：
- ビフォーを置いた人と別の人がアフターを付けた場合に、実際に手を動かした人名が入る
- status は `completed` のまま。`status == "helped_by"` という値は**存在しない**ので注意

### 既存エンドポイント（抜粋）

| メソッド | パス | 役割 |
|---|---|---|
| GET | `/maintenance` | 全記録（新しい順・最大50） |
| GET | `/maintenance/zone/{zone_id}` | ゾーン別記録 |
| POST | `/maintenance` | 投稿（ビフォー/アフター） |
| PATCH | `/maintenance/{id}/complete` | ビフォーにアフターを付けて完了（`helper_name`で受け渡し記録） |
| GET | `/zones` | ゾーン一覧 |
| GET | `/admin/thanks` | ありがとう一覧（最大200） |
| POST | `/thanks/{maintenance_id}` | 手動ありがとう |

### 既存フロント
- `pwa/index.html` … 単一画面（ヘッダー＋ゾーンバナー＋フィード＋各種モーダル）
- `pwa/app.js` … フィード描画・投稿・ありがとう・人の蓄積シート
- ゾーンページは `/zone/{zone_id}` で開く。`main.py` が `index.html` を返し、`app.js` が URL からゾーンIDを取得して `/maintenance/zone/{id}` を読む

## 2. 追加するもの

### 2-1. 概念：タイムライン＝手入れ（維持・改変）の連なり

タイムラインに並ぶのは **`care`（手入れ）イベント1種類のみ**。`maintenance` 1件＝1イベント。維持（掃除）も改変（造作）も区別せず、同じカードとして時系列に並べる。

ありがとう（`thanks`）は独立したイベントにはしない。各 `care` イベントに**付随する反応**として、その手入れカードの中に表示する（送り主・ひとことメッセージ）。

> 補足：「利用（誰がその場所を使ったか）」は本仕様では扱わない。**ありがとうが送られたこと自体が「その手入れが役に立った」跡**を兼ねるため、利用を別途記録・表示しない。

### 2-2. 新エンドポイント

```
GET /zones/{zone_id}/timeline
```

**役割：** ある場所の手入れ記録を、各記録に紐づくありがとうを添えて、時系列（新しい順）で返す。クライアントで `maintenance` と `thanks` を突き合わせる負担をなくす。

**レスポンス例：**

```json
{
  "zone": { "id": "z1", "name": "ゼミ室・本棚まわり" },
  "summary": {
    "care_count": 12,
    "contributor_count": 5,
    "first_care_at": "2026-05-02T10:11:00+09:00",
    "last_care_at":  "2026-06-13T18:40:00+09:00"
  },
  "events": [
    {
      "type": "care",
      "id": "m_abc",
      "person_name": "木場 太郎",
      "helped_by": null,
      "before_photo": "https://storage.googleapis.com/.../b.jpg",
      "after_photo":  "https://storage.googleapis.com/.../a.jpg",
      "status": "completed",
      "thanks_count": 3,
      "thanks": [
        { "sender_name": "小島 花子", "message": "助かった", "created_at": "2026-06-13T19:02:00+09:00" }
      ],
      "created_at": "2026-06-13T18:40:00+09:00"
    }
  ]
}
```

**実装メモ：**
- `maintenance` を `zone_id` で取得（既存の `where("zone_id","==",...)` 方式。複合インデックス回避のためサーバ側で `created_at` 降順ソート）
- 各記録に紐づく `thanks`（`source` は問わない）を `maintenance_id` で集約して `thanks` 配列に入れる
- 写真は既存 `photo_url()` で完全URL化
- `summary.care_count` = そのゾーンの `maintenance` 件数
- `summary.contributor_count` = `person_name` ∪ `helped_by` のユニーク数
- `summary.first/last_care_at` = `created_at` の最小・最大

### 2-3. UI：ゾーンページのタイムライン

既存のゾーンバナーの下を「フィード」から「タイムライン」に差し替える。

**画面構成（縦）：**

```
┌──────────────────────────────┐
│ ZONE                          │
│ ゼミ室・本棚まわり             │  ← 既存バナー（貢献者アバターは残す）
├──────────────────────────────┤
│ この場所のこれまで             │
│ 手入れ12回 · 5人               │  ← summary 帯（評価語を入れない。数だけ）
│ 5/2 から 6/13 まで            │
├──────────────────────────────┤
│ ● 6/13 18:40  木場太郎         │
│   [BEFORE/AFTER 写真]          │  ← care イベント（写真タップでB/A切替・既存流用）
│   🙏 小島花子「助かった」       │  ← その手入れに付いたありがとう
│                                │
│ ● 6/10 12:30  山田花子          │
│   ↳ 木場の「気になる」に応えた  │  ← helped_by があれば受け渡しを明示
│   [写真]                       │
│                                │
│ ● 5/2 10:11  木場太郎          │  ← 一番古い手入れ（連なりの起点）
│   [写真]                       │
└──────────────────────────────┘
```

**表示ルール：**
- **時系列は縦の一本線**（左に縦線を引き、各 `care` を●＋写真つきカードで並べる）。これで「変遷＝連なり」が視覚的に出る
- **care カード：** 既存のカード描画（ビフォー/アフター切替、ありがとうフロート、送り主アバター）を流用
- **受け渡し：** `helped_by` があれば「↳ {person_name} の『気になる』に応えた」をカードに表示（実装済みの handoff 表記を流用）
- **評価語を書かない：** 「綺麗になった」等のシステム生成文言は入れない。事実（誰が・いつ・写真）のみ

**並び順：** 新しい順（最新の手入れが上）。summary には「最初の手入れ → 最新の手入れ」の期間を出し、**積み重ねの長さ**が一目で分かるようにする。

### 2-4. ルーティング
- 既存どおり `/zone/{zone_id}` でこの画面を開く
- `app.js` の初期化で、ゾーンページのときは `loadFeed()` ではなく新規 `loadTimeline(zoneId)` を呼ぶ
- トップ（ゾーン無し）は従来のフィードのまま

## 3. スコープ外（今回やらないこと）

- **利用（use）の記録・表示**（ありがとうが跡を兼ねるため不要）
- 場所をまたいだ集計・ランキング
- 地図・QR/NFC連携（別仕様。タイムラインができてから）
- 「次どこをいじるべき」の提案・指示（思想上やらない。隙間は現場で見つける）

---

## 4. 受け入れ条件（Definition of Done）

1. `GET /zones/{zone_id}/timeline` が、ゾーンの手入れ記録＋各記録のありがとうを時系列で返す
2. `/zone/{zone_id}` を開くと、その場所の手入れが一本の時系列で並ぶ
3. summary に「手入れ回数・貢献者数・期間」が出る
4. care カードは既存のビフォー/アフター切替・ありがとう・受け渡し表記が機能する
5. システム生成の評価語（「綺麗」等）が画面に一切出ない
6. 記録ゼロの場所では「まだこの場所の記録はありません」を出す

---

## 5. 補足：研究上の意図（実装判断で迷ったとき用）

- このタイムラインは**研究データの可視化**でもある。「最初のありがとうまでの時間」「手入れ→次の手入れの間隔」「受け渡し率」が読み取れる形だと望ましい
- 思想の核：**アプリは環境を説明しない。環境に起きた事実を並べ、判断は身体（現場）に返す。** UIで悩んだら「これは説明か、事実か」で判断する。説明なら削る
- 並ぶのは手入れ（維持・改変）の連なり。その積み重ねが「場所の変遷」として見えることが、次の人の手を呼ぶ着火源になる
